R4 requirements reconciled 13 October 2026 from audit starting app head `b160656218dc6065ad12af9db220c974255bfc23`. The original plan reviewed Keeper `0550ac9ffa938a079816ae4ed58bc970324c3e08` and Relay PR #4 `82ee3b10708a56d220170505d1bb7e3bc8429e77`; those are historical inputs, not the final proof source.

The owner requires the automatic-backup fix and disposable proof in R4. Critical native IOS/ANDROID backup checks also precede release; explicitly physical-only follow-up may be recorded separately. This plan authorizes no production enablement, merge or Relay deployment. Source implementation must stay fail-closed until committed-payload/session proof and the required disposable matrix pass. Record current implementation and results in [automatic-write-validation.md](automatic-write-validation.md); no future gate is marked complete here.

## Why the audit-baseline intent cannot authorize a write

At the audit starting source, `BackupWriteIntent` records the selected account session and a previously verified Relay revision. It does not identify the local recovery state represented by an encrypted payload or deletion. `backupPost` therefore rejects all seven operations before network. This is required at that baseline: some producers encrypt action data before Realm persistence, Realm may change while an action waits, and one action can emit several Relay writes with the same captured base revision. A valid server compare-and-swap protects against another server writer; it does not prove that the client is sending its present local recovery data. Later implementation/proof must update the result matrix; these observations are not a claim about its final source.

The baseline central Realm observer invalidates backup verification **before** each relevant write. It has no post-commit token and can fire for several field writes in one logical action. The baseline transport's `queuedMutationRevisions` is never populated, so it cannot provide a queue completion proof. A pre-send comparison of a prepared ciphertext against the current Realm image is necessary but still insufficient for operations deliberately sent before local persistence.

## Required transaction model

1. Give each logical local recovery operation an account-scoped operation ID and a commit result. A successful commit captures a monotonic recovery generation after all related Realm writes; failed or partial writes stay pending and never authorize upload. For pre-persistence producers, stage data locally and queue the cloud mutation only after this commit. Do not make server success a prerequisite for saving a new wallet, signer, vault or deletion.
2. Capture the originating `appId`, account session, verified base revision/epoch and operation ID before async work. Never substitute a newly verified base for an older action. On A→B→A, reject old queued work even if A is selected again. An already sent request has an uncertain outcome and requires readback.
3. At the head of the per-account queue, re-read the fresh local recovery image and prove the proposed operation's decrypted payload or deletion target against that image and its committed generation. Verify the selected account, backup consent, encryption key ownership, and the originally captured session immediately before sending. An operation-specific failed proof ends in pending/unverified without network.
4. Read or retain a validated v2 Relay snapshot and its 64-character revision. No legacy endpoint fallback. Apply each proposed operation to the remote snapshot in memory and reject an effect that removes remote-only recovery records or changes key identity without an explicit user decision. The Relay must atomically enforce `expectedRevision` and return `updated: true`, `preconditionApplied: true` and a valid `newRevision`.
5. A multi-record logical operation should use one Relay transaction carrying all its effects. If the existing v2 route is used sequentially, each step must validate its own current local proof and use the preceding acknowledged `newRevision`. Partial success remains pending. Never call the whole backup verified on an intermediate response.
6. After the last acknowledged write, read back and decrypt the complete Relay image. Only a match with a newly captured local image at the same committed generation may set verified. A local write during comparison invalidates the claim. The existing atomic Redux verification commit remains the final UI gate.
7. On 409, old Relay/404, malformed acknowledgement, timeout, lost response, network error, failed local commit, changed session or changed local generation, stop the chain. Do not retry prepared ciphertext or send later fanout members. Keep pending and run a read-only check. A lost response may have committed on the server; its result must be learned from readback before any fresh write.

## Operation-specific proof at the queue head

| Relay operation | Local proof before send | Audit-baseline producer complication |
| --- | --- | --- |
| `updateAppImage` | Decrypt each wallet/USDT/signer ciphertext with the active account seed; map IDs, sanitized signer records and recoverable fields must equal the committed Realm records. `replaceNodes` requires the exact current normalized node set; app metadata must come from the current KeeperApp. | New wallet and signer creation call backup before Realm insertion. Node and version paths use different timing. Action payloads may be stale. |
| `migrateXfps` | Old exact KeyUID must be absent in committed Realm; new exact KeyUID and decrypted sanitized signer must match Realm. Verify all affected vault signer references, and prove the old map entry exists in the validated Relay snapshot. | The worker updates a live signer before building the request. It previously sent bare fingerprints while Relay maps use KeyUIDs; a narrow key fix is included separately, with transport still disabled. |
| `deleteAppImageEntity` | Every wallet/USDT/signer ID must be absent after a successful local commit and present in the expected Relay snapshot. Deleting a signer must not make a retained vault unrecoverable. | BTC wallet and signer deletion currently calls Relay before Realm deletion; USDT deletion also does so directly. Moving this order requires durable pending state and truthful result/UI handling. |
| `deleteVaults` | Each ID must be absent after local commit; other participant/shared-vault references must remain owned and recoverable. | Vault deletion also calls Relay before local deletion. A remote success followed by local failure can leave a mismatched backup. |
| `updateVaultImage` | Decrypt the vault; its ID, sanitized signers, policy, archive state and `signersData` must match the committed Realm Vault plus persisted VaultSigner registrations. | Creation and metadata edit can call Relay before persistence. Registration changes can fan out to several vault writes; migration creates and archives two vaults. |
| `modifyLabels` | Decrypt each added label and verify the account-derived hashed ID and current Realm tag. Every deleted hashed ID must map to a tag absent after local commit. Reconcile add/delete overlap and account ownership. | Imports, upgrades and transaction-label workers can emit multi-label fanouts; a delayed file callback carries older intent. |
| `deleteBackup` | Require an explicit opt-out action for the same selected account and session, a fresh v2 revision, and exact whole-account target. Preserve consent until a positive v2 acknowledgement; on lost response use readback without claiming success. | This is a destructive exception to the local-image comparison: the user intentionally removes the remote copy while keeping Realm. It needs its own opt-out state and separate tests. |

## Test matrix before any enablement

Run each of the seven operations against disposable Realm and transactional Relay fixtures, with real encryption/decryption and the production saga/transport entry points. For each operation, verify: matching committed payload/target reaches the v2 route once; stale payload after a local mutation sends nothing; A→B→A sends nothing; a server 409/old route 404/malformed response leaves pending and does not fall back; timeout or lost acknowledgement sends no next item and readback cannot create false verified. Exercise both matching and remote-only/conflicting snapshots.

Add focused multi-write fixtures for (a) creating and archiving a vault, (b) one VaultSigner registration affecting several vaults, and (c) label import plus deletion. Make the first Relay write succeed and the next fail; assert local data survives, the remaining prepared writes do not run, and neither a saga nor Redux reports verified. Assert a local mutation injected just before the final verification commit leaves the backup pending. Pair these tests with native iOS/Android create, edit, delete, relaunch and clean Recovery Key restore on the exact app SHA, plus Relay v2 HTTP tests against a disposable replica set.

Keep automatic source transport fail-closed until this matrix passes. Production delivery additionally requires verified transaction topology, compatible running Relay artifacts and protection from old/legacy writers under separately authorized rollout; a source pass is not deployment evidence. A future source change must never turn an endpoint name or revision string alone into a freshness proof. The current result matrix also tracks mandatory native and clean Recovery Key restore checks independently of fixture outcomes.
