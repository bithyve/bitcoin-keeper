The seed store remains a **diagnostic preview foundation**. Android uses Keystore-encrypted no-backup storage under process/file locks, bounded authenticated records and durable readback. iOS uses a non-synchronizing WhenUnlockedThisDeviceOnly Keychain item and create-if-absent/readback. Both now expose a read-only operation that never creates a missing record. Generated/owned mutable buffers are cleared on exits, but immutable native/base64/JavaScript strings and BIP32 copies cannot be reliably erased. These are not non-exportable or proven hardware-backed signing keys; independent security review is required before activation.

The two-read evidence proves only an immediate public identity match. It always reports `backupVerified: false`, `recoveryVerified: false` and `walletReady: false`. Record public values externally before restart/reinstall testing; do not treat a matching short display tag as a policy or recovery authorization.

`previewMobileKeyBackup.ts` is a **local-fixture-only foundation**, disconnected from the app. It requires 32 independently generated recovery-secret bytes, fresh salt/nonce requests, fixed bounded crypto parameters and an independently held complete base testnet policy. Verification authenticates the envelope and re-derives the exact fingerprint/account tpub from the decrypted 32-byte seed, returning evidence only. It never returns/imports a seed or replaces native storage. All results keep `cloudBackupVerified`, `nativeRestoreVerified` and `walletReady` false. Inheritance is rejected until its separate recovery validation exists. Actual credential custody, policy persistence, rollback protection and cloud/native restore remain future work.

## Non-negotiable product model

- One Wallet within Keeper; not a replacement for whole-app recovery with the twelve-word **Recovery Key**.
- Standard base **2-of-3 Mobile Key + user-selected Hardware Key + Server Key**. Mobile/Server status is presented automatically; no manual quorum builder.
- Hardware added last among the base keys, using appropriate physical connection, QR or NFC flow.
- Optional Inheritance Key is chosen before final wallet-policy approval. The *final complete* policy is confirmed once; don't fund/register an intermediate wallet.
- Plain base 2-of-3 is not Bitme's timelocked Miniscript descriptor. When inheritance is added, use Keeper's Miniscript policy with compatibility testing for **all** signers. Signing-only hardware (TAPSIGNER/Satochip) is distinct from policy-verifying hardware.
- After inheritance eligibility, independent heir's Inheritance Key + any eligible original signer can form the required 2-of-4 quorum; Keeper server cannot become mandatory for the heir's exit path.
- Cloud encrypted Mobile Key backup in user's iCloud / Google Drive is separate from existing Personal Cloud Backup. Its "healthy" status must be based on cryptographic read-back, not request success.
- Hardware-authorised unlocking via server-held recovery material is an accepted trade-off; design, isolation, replay protection and threat model require independent security review before real funds.
- Contact-based recovery must ultimately be **independent of Keeper's server** if an enrolled contact + accessible encrypted cloud backup are available.
- Hardware + Server supports delayed replacement of missing Mobile Key when cloud backup is missing, once server implementation is allowed.
- Mobile + Hardware and descriptor support server-independent spending/exit. Test actual external-wallet compatibility; public descriptors do not contain private keys.
- Key changes mean new wallet policy and on-chain transfer with fee and original-wallet authorization. Archive the complete predecessor and monitor retained archived addresses indefinitely, including zero-balance wallets. Do not archive merely because the same Mobile Key was restored.
- Keep Recovery Contact distinct from signing keys and Inheritance Key. The existing 12-word Recovery Key is an **additional option**, not a mandatory prerequisite or a message on the Assisted Multisig choice. Do not imply it can reproduce an independently generated Mobile Key without an encrypted copy or other reviewed recovery mechanism.

## How the owner will test it

Deliver a **separate-installation iOS and Android Keeper Preview** (different app identity and storage namespace from production Keeper), testnet-only and isolated from real iCloud/Google Drive backups. Verify the necessary app IDs, native entitlements, cloud containers and distribution access before promising TestFlight or Android APK builds. Keep normal Keeper installed and unaffected. Preview actions may initially be mocked: they must be unmistakably identified as simulated; no fake success, funding or cryptographic-security claims.

A new preview checkpoint is complete **only after an installable build and a short device-specific owner test checklist are available**, and after actual tests are recorded:

1. **Prototype/UI**: start on empty Wallets or use Add Wallet, choose Assisted Multisig, then review hardware picker/connection, automatic Mobile/Server status, optional inheritance, and one final policy; include errors/cancel/resume.
2. **Disposable real wallet**: create fixed 2-of-3 wallet on testnet using supported available signers, safely receive/send test sats, inspect proper fees and outputs. No mainnet, no production credentials.
3. **Backup**: encrypted Mobile Key recovery blob, versioning, iCloud/Drive isolation, read-back verification, retry/offline/background/interrupted write tests; retain existing Keeper backup compatibility.
4. **Recovery via hardware**: lose/reinstall disposable preview, prove hardware possession, restore same wallet and explain retain-versus-rotate Mobile Key after restoration. This requires reviewed server protocol; do not simulate as if implemented.
5. **Recovery Contact**: enroll second person/device, approve/decline, backup/reinstall contact credential; recover when Keeper server is demonstrably unreachable. Actual independent channel/crypto is required for completion.
6. **Lost-key, inheritance and exit**: delay/veto/replacement, migration/archive/old deposit, Miniscript policy registration and exact signer paths, descriptor export plus actual compatible external-wallet sweep, with Keeper server offline.
7. **Hardening and mainnet-readiness**: comprehensive adversarial/destructive tests; iOS/Android real NFC/QR hardware and app life-cycle, independent crypto/security review, full regression against then-current Keeper build. Mainnet activation and campaign only after explicit user approval.

Each checkpoint may be smaller than the grouping above to keep visible feedback frequent. Keep a clean recorded matrix of **simulated / automated / native / physical / security-reviewed / user-tested**, never conflating these.

## Hardware-wallet incident lessons: release safety and marketing (11 October 2026)

Owner instruction: the Assisted Multisig buildup must account for the July 2026 COLDCARD entropy incident and the October 2026 Ledger reseller-tampering reports. This is a durable product and communication rule, not an opportunity to attack affected manufacturers or users.

- **COLDCARD entropy:** Device firmware versions that generated weak seeds may leave those *existing seeds* exposed even after a firmware update. Migration to a fresh, independently generated signer key and, when necessary, a new wallet policy/on-chain transfer is the relevant remedy, subject to the maker's official advisory. Check actual model, firmware release track, and **when/how the seed was originally generated**, not merely today's firmware version. Do not claim Keeper or multisig can 'fix' an already compromised key. Source: https://coldcard.com/security/status and https://github.com/Coldcard/firmware/blob/master/README.md
- **Ledger incident:** October 2026 reports concern possible supply-chain tampering of devices from a particular reseller; as of this note, ongoing investigation/claims about total losses must be described as **reported/unconfirmed**, not a proven Ledger-wide firmware/secure-element failure. Source: https://www.theverge.com/tech/1009294/ledger-wallet-tampering-suspected-after-reports-of-crypto-thefts and https://www.coindesk.com/business/2026/10/09/ledger-investigates-potential-wallet-tampering-after-reports-of-usd86-million-in-crypto-stolen
- **Threat-model truth:** Standard 2-of-3 means one exposed key alone does not meet the spending threshold, assuming the other two remain independently secure. A compromised device, fake device, malicious coordinator/PSBT, unsafe seed, or combined compromise of Mobile Key + Server Key are still real risks; hardware freedom does not inherently establish device authenticity, entropy strength or signer independence. Our server-assisted recovery trade-off must be disclosed without claiming security superiority.
- **UX and testing acceptance:** Before describing any hardware as "verified"/"safe", check the supported device, exact transport and firmware capabilities, source/provenance, compromised-seed history, policy-aware confirmation vs digest-only signing, and independent transaction/output/change verification where device permits. Document and test warning + optional migration/rotation paths for known affected signer keys, preserving original-wallet signing and archive monitoring. Do not automatically classify device as secure because current firmware is patched; a user-visible unknown status must remain unknown.
- **Public campaign editorial rule:** Name Ledger/COLDCARD only when useful to explain *specific and sourced* failure modes and what users should do, keeping active investigations qualified. Separate impartial incident explainers from Assisted Multisig product promotion. Avoid "Ledger hacked", "COLDCARD broken", "your hardware is no longer trustworthy", "multisig stops hacks", "seedless avoids this", "guaranteed recovery", or incident-driven scare tactics. No unsolicited posts targeted at people reporting losses. Offer practical checks first; discuss the merits and residual risks of independent signers only with qualified, tested claims.
- **Launch proof:** Campaign must not advertise verified signer independence, manufacturer support, secure cloud/contact recovery, protection against hardware compromises, or improved security until real physical/iOS/Android tests and independent review support each specific statement.
